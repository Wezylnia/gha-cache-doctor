# Implementation Roadmap To v0.7

This document is written for an implementation agent that needs explicit, low-ambiguity instructions. Follow it in order. Do not skip validation, documentation, or release steps.

Current baseline: `v0.4.0`.

Primary project shape:

- CLI entry point: `src/GhaCacheDoctor.Cli/Program.cs`
- Core models and scanner: `src/GhaCacheDoctor.Core/`
- GitHub Actions parser and cache rules: `src/GhaCacheDoctor.GitHubActions/`
- Reporters: `src/GhaCacheDoctor.Reporters/`
- Tests:
  - `tests/GhaCacheDoctor.Core.Tests/`
  - `tests/GhaCacheDoctor.GitHubActions.Tests/`
  - `tests/GhaCacheDoctor.Cli.Tests/`
- Rule docs: `docs/rules/`
- Samples: `samples/github-actions/good/` and `samples/github-actions/bad/`

## Global Rules For Every Version

Use these rules for every task in this document.

1. Start each version from a clean `main`.
   ```bash
   git status --short
   git pull --ff-only origin main
   ```
2. Create a dedicated branch for the version.
   ```bash
   git switch -c release/v0.5.0
   ```
3. Keep commits small and reviewable. Prefer this order:
   - one commit for rule/model/parser changes,
   - one commit for reporter/CLI changes if applicable,
   - one commit for samples and tests,
   - one commit for documentation and version metadata.
4. Never commit generated output from `bin/`, `obj/`, `.tmp/`, or local tool installs.
5. For every new rule:
   - add one rule class under `src/GhaCacheDoctor.GitHubActions/Rules/`,
   - register it in `GitHubActionsRules`,
   - add the rule title to `src/GhaCacheDoctor.Reporters/RuleTitles.cs`,
   - add focused unit tests in `tests/GhaCacheDoctor.GitHubActions.Tests/CacheRuleTests.cs` or a new rule-specific test file,
   - add at least one bad sample and, when useful, one good sample,
   - add one docs page under `docs/rules/`,
   - update `docs/rules/README.md` and the README rule table.
6. For every user-visible CLI or config change:
   - update README CLI reference,
   - update `docs/configuration.md` if config is affected,
   - add CLI tests in `tests/GhaCacheDoctor.Cli.Tests/CliApplicationTests.cs`,
   - add reporter tests if output changes.
7. Before each commit, run:
   ```bash
   dotnet build GhaCacheDoctor.slnx
   dotnet test GhaCacheDoctor.slnx
   git diff --check
   git status --short
   ```
8. Before release, run the release validation exactly:
   ```bash
   dotnet restore
   dotnet build GhaCacheDoctor.slnx --configuration Release
   dotnet test GhaCacheDoctor.slnx --configuration Release --no-build
   dotnet pack src/GhaCacheDoctor.Cli --configuration Release --no-build
   dotnet run --project src/GhaCacheDoctor.Cli -- scan --path samples/github-actions/bad --fail-on none
   dotnet run --project src/GhaCacheDoctor.Cli -- scan --path samples/github-actions/bad --format json --fail-on none
   dotnet run --project src/GhaCacheDoctor.Cli -- scan --path samples/github-actions/bad --format markdown --fail-on none
   dotnet run --project src/GhaCacheDoctor.Cli -- scan --path samples/github-actions/bad --format sarif --fail-on none
   dotnet run --project src/GhaCacheDoctor.Cli -- scan --path samples/github-actions/bad --format github-annotations --fail-on none
   ```
9. Local package smoke test before release:
   ```bash
   if (Test-Path .tmp/tools-vNEXT) { Remove-Item -LiteralPath .tmp/tools-vNEXT -Recurse -Force }
   dotnet tool install --tool-path .tmp/tools-vNEXT gha-cache-doctor --version NEXT_VERSION --add-source src/GhaCacheDoctor.Cli/bin/Release
   .tmp/tools-vNEXT/gha-cache-doctor scan --path samples/github-actions/bad --fail-on none
   ```
10. Release only after main CI is green.

## v0.5.0 - Broader Cache Coverage

Goal: detect common cache misses outside Node, Python, and Gradle. Keep the release rule-focused and avoid changing CLI behavior.

### Task 1: Add .NET NuGet Cache Opportunity Rule

Rule ID: `GHA-CACHE008`

Rule title: `dotnet-cache-missing`

Severity: `info`

Category: `performance`

Files to touch:

- Add `src/GhaCacheDoctor.GitHubActions/Rules/DotNetCacheMissingRule.cs`
- Update `src/GhaCacheDoctor.GitHubActions/Rules/GitHubActionsRules.cs`
- Update `src/GhaCacheDoctor.Reporters/RuleTitles.cs`
- Update `tests/GhaCacheDoctor.GitHubActions.Tests/CacheRuleTests.cs`
- Add `docs/rules/GHA-CACHE008-dotnet-cache-missing.md`
- Update `docs/rules/README.md`
- Update README rule table

Detection behavior:

- Report when a job runs a dependency restore or build command that implies NuGet restore and no cache step exists earlier in the same job.
- Treat these commands as restore signals:
  - `dotnet restore`
  - `dotnet build` without `--no-restore`
  - `dotnet test` without `--no-restore`
  - `dotnet publish` without `--no-restore`
- Treat any earlier step as NuGet cache configured if it uses `actions/cache` and caches one of:
  - `~/.nuget/packages`
  - `${{ env.NUGET_PACKAGES }}`
  - a path containing `.nuget/packages`
- Do not report if the job uses `setup-dotnet` only. `setup-dotnet` does not configure dependency caching by itself.
- Do not report if the only commands are `dotnet build --no-restore` or `dotnet test --no-restore`.

Recommendation text:

```text
Cache the NuGet package folder before restore, for example actions/cache with path `~/.nuget/packages` and a key based on `hashFiles('**/*.csproj', '**/packages.lock.json', '**/global.json')`.
```

Minimum tests:

- reports `dotnet restore` with no cache,
- reports `dotnet build` without `--no-restore`,
- does not report `dotnet test --no-restore`,
- does not report when `actions/cache` for `~/.nuget/packages` appears before restore,
- reports when cache appears after restore,
- includes job id, step name, file path, and line when available.

Commit:

```bash
git add src tests docs README.md
git commit -m "feat: add dotnet cache rule"
```

### Task 2: Add Docker BuildKit Cache Opportunity Rule

Rule ID: `GHA-CACHE009`

Rule title: `docker-buildkit-cache-missing`

Severity: `info`

Category: `performance`

Files to touch:

- Add `src/GhaCacheDoctor.GitHubActions/Rules/DockerBuildKitCacheMissingRule.cs`
- Update `GitHubActionsRules.cs`
- Update `RuleTitles.cs`
- Add tests
- Add `docs/rules/GHA-CACHE009-docker-buildkit-cache-missing.md`
- Update rule catalog and README

Detection behavior:

- Report when a job uses `docker/build-push-action` without either `cache-from` or `cache-to`.
- Report when a run step contains `docker buildx build` without either `--cache-from` or `--cache-to`.
- Do not report plain `docker build` in v0.5. It may not use BuildKit and would create false positives.
- Do not report when `cache-from` and `cache-to` are both present.
- Use warning only if strict mode is enabled and the job clearly builds an image on every push to `main`; otherwise keep info.

Recommendation text:

```text
Add BuildKit layer caching, for example `cache-from: type=gha` and `cache-to: type=gha,mode=max` for docker/build-push-action.
```

Minimum tests:

- reports `docker/build-push-action` without cache fields,
- does not report when both cache fields are present,
- reports `docker buildx build` without flags,
- does not report `docker buildx build --cache-from ... --cache-to ...`,
- does not report plain `docker build`.

Commit:

```bash
git add src tests docs README.md
git commit -m "feat: add docker buildkit cache rule"
```

## v0.7.0 - Baselines And Suppressions

Goal: make adoption easier for repositories that already have many findings. This release should not add many new rules. It should add workflow controls for gradual rollout.

### Task 1: Add Baseline File Support

Config field:

```yaml
baseline: .gha-cache-doctor-baseline.json
```

CLI option:

```text
--baseline <path|none>
```

Files to touch:

- `src/GhaCacheDoctor.Core/ScanOptions.cs`
- `src/GhaCacheDoctor.Cli/Program.cs`
- config loader code in the CLI project
- `tests/GhaCacheDoctor.Cli.Tests/CliApplicationTests.cs`
- `docs/configuration.md`
- README CLI reference

Behavior:

- A baseline suppresses matching existing findings.
- Matching key should include:
  - rule id,
  - normalized file path,
  - job id when present,
  - step name when present,
  - message hash or stable message text.
- Do not include line number in the matching key. Line numbers move too often.
- Baseline suppressions must not remove parse errors.
- If the baseline file does not exist, return CLI usage error exit code `2` with a clear message.

Baseline JSON shape:

```json
{
  "version": 1,
  "findings": [
    {
      "ruleId": "GHA-CACHE003",
      "filePath": ".github/workflows/ci.yml",
      "jobId": "build",
      "stepName": "Cache npm",
      "message": "actions/cache uses a dependency cache path, but the key does not include a lockfile hash."
    }
  ]
}
```

Minimum tests:

- matching finding is suppressed,
- non-matching finding remains,
- parse error remains,
- missing baseline file returns exit code `2`,
- config baseline is used when CLI baseline is not provided,
- `--baseline none` disables config baseline.

Commit:

```bash
git add src tests docs README.md
git commit -m "feat: add baseline suppression support"
```

### Task 2: Add Baseline Generation Mode

CLI option:

```text
--write-baseline <path>
```

Behavior:

- Run the scan normally.
- Write all current findings to the baseline file.
- Do not write parse errors into the baseline.
- Create parent directory if needed.
- Output should still render according to `--format`.
- Exit code should be based on findings before suppression unless `--baseline` is also supplied.
- If both `--baseline existing.json` and `--write-baseline new.json` are supplied:
  - suppress existing baseline matches,
  - write remaining findings to the new baseline.

Minimum tests:

- writes valid JSON baseline,
- creates parent directory,
- excludes parse errors,
- can write remaining findings after applying an existing baseline.

Commit:

```bash
git add src tests docs README.md
git commit -m "feat: add baseline generation"
```

### Task 3: Add Inline Suppression Comments

Supported syntax in workflow YAML comments:


Scope:

- `disable-next-line` suppresses findings on the next non-empty line.
- `disable-file` suppresses the rule for the entire file.
- If a finding has no line number, only file-level suppression can suppress it.

Minimum tests:

- next-line suppression suppresses exactly one finding,
- file suppression suppresses all matching rule findings in a file,
- unrelated rule is not suppressed,
- invalid rule id comment is ignored.

11. Create and push the tag.
